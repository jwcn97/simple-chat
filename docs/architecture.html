Simple Chat Architecture

A WebSocket chat backend built as a system-design learning exercise: token-based auth with an isolated signing key, Redis pub/sub for live delivery, and a Cassandra (Amazon Keyspaces) store deliberately sharded two different ways for two different queries.

Node.js ws Redis pub/sub Amazon Keyspaces RS256 / JWT Argon2id

01 — topology

Who talks to whom

Two kinds of connection, and they never overlap: clients hit auth.js once over plain HTTP to get a token, then hold a persistent WebSocket open to one of several interchangeable gateway.js instances. Redis and Keyspaces are shared infrastructure underneath every gateway — none of it is gateway-specific state, which is exactly what lets you run more than one gateway at all.

02 — durability path

What "sent" actually guarantees

Every send does a durable write before it does anything best-effort. That ordering is the whole reliability story: if the publish step never reaches anyone — recipient offline, Redis hiccup, doesn't matter — nothing is lost, because the message was already safe before the publish was attempted. Catch-up on reconnect just re-reads what step 3 already saved.

03 — data model

One set of messages, two shardings

messages_by_conversation and inbox_by_user store overlapping data on purpose. "Load this conversation's history" wants everything grouped by conversation_id; "catch me up across every conversation I'm in" wants everything grouped by user_id instead. No single partition key satisfies both, so every send writes to both tables rather than forcing one query to be slow.

04 — decisions worth remembering

Choices that weren't the obvious default

  • RS256, not HS256, for the JWT

    With a shared HMAC secret, every gateway would need it to verify tokens — and any one compromised gateway could then forge tokens for the whole system. RS256 means only auth.js ever holds the private key; gateways hold only the public key, so they can verify but never mint.

  • A standalone auth.js, not a route on gateway.js

    Folding login into the gateway would have put the private key on every gateway instance too, quietly undoing the reason RS256 was chosen in the first place.

  • Cursor is (timestamp, message id), not timestamp alone

    A millisecond timestamp round-tripped through JS's Date.getTime() loses precision Postgres/Cassandra actually store, which caused already-seen messages to look "new" again on reconnect. The message id has no precision to lose.

  • Group fan-out is per-recipient best-effort, not all-or-nothing

    Promise.allSettled, not Promise.all — one recipient's failed inbox write shouldn't make the gateway treat an otherwise-successful send as a total failure.

  • Subscribe before catch-up query, not after

    Querying history first and subscribing second leaves a gap where a message published in between is caught by neither — a permanent loss. Subscribing first can only ever produce a duplicate in that gap, which the client already dedupes by message id.

  • Small bounded groups, not large channels

    Fan-out-on-write doesn't survive a 100,000-member send. That's the fan-out-on-read problem real broadcast platforms solve — deliberately out of scope here.

05 — running it

Three processes, one Redis

Full setup (AWS Keyspaces provisioning, key generation) is in the README — this is the day-to-day loop once that's done.

infra cd server && docker compose up -d
auth npm run auth
gateways npm run gateway -- 3001 gateway-1 npm run gateway -- 3002 gateway-2
clients npm run client -- alice pw 3001 --signup npm run client -- bob pw 3002 --signup
simple-chat — a system design learning project. See ../README.md for setup.
